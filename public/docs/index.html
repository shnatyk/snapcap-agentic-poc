Agentic workflow na GitHubie

Opisujesz pomysł w zgłoszeniu (issue) na GitHubie i dodajesz etykietę idea. Resztę robią agenci AI (Claude): dopytują o szczegóły, rozpisują zadanie, piszą kod z testami i sprawdzają nawzajem swoją pracę. Ty wchodzisz do gry w trzech momentach.

Strona tłumaczy, jak to działa, i prowadzi krok po kroku przez konfigurację nowego repo. Aplikacja w repo to prosta lista zadań. Jej prawdziwym celem jest wypróbowanie tego procesu.

idea→ grilled→ backlog→ PR→ reviewed→ done→ Approve→ merge

Co robisz Ty

  1. 1

    Odpowiadasz na pytania

    Agent pyta w komentarzach pod issue. Odpisujesz, aż wszystko będzie jasne. Na końcu potwierdzasz jego podsumowanie słowem „ok”.

  2. 2

    Testujesz podgląd

    Gdy agenci skończą, dostajesz prośbę o review PR-a. W komentarzu jest link do podglądu aplikacji z tą zmianą. Klikasz i sprawdzasz.

  3. 3

    Akceptujesz albo odsyłasz

    Approve: zmiana sama trafia do master i na stronę. Request changes z uwagami: agent je wprowadza i wraca do Ciebie.

Kilka pojęć na start

Issue
Zgłoszenie na GitHubie: pomysł, błąd albo zadanie. Ma opis, komentarze i etykiety.
Etykieta (label)
Kolorowy znacznik na issue albo PR-ze. Tutaj działa jak przełącznik: dodanie etykiety uruchamia kolejnego agenta.
Pull request (PR)
Propozycja zmian w kodzie. Ktoś ją przegląda i scala (merge) z główną gałęzią master.
GitHub Actions
Automaty GitHuba. Plik workflow (.yml) mówi: „gdy stanie się X, uruchom Y”. Działają na serwerach GitHuba, nie na Twoim komputerze.
Agent
Claude Code uruchomiony w GitHub Actions. Czyta repo i wątek, wykonuje komendy, pisze kod i komentarze. Nikt go nie nadzoruje w trakcie, więc drobne decyzje podejmuje sam i je zapisuje.
Skill
Gotowa instrukcja pracy dla agenta, np. /grill-with-docs albo /tdd. Korzystamy ze skilli Matta Pococka.
claude[bot]
Konto, którym agenci działają na GitHubie. Daje je aplikacja Claude GitHub App.
Podgląd (preview)
Wersja aplikacji z danego PR-a, opublikowana pod osobnym adresem na GitHub Pages. Znika po merge'u.

Jak pomysł przechodzi przez proces

Każdy etap to osobny plik w .github/workflows/. Etykieta ustawiona na końcu jednego etapu uruchamia następny.

  1. 1

    Pomysł

    Ty

    Zakładasz issue z krótkim opisem pomysłu i dodajesz etykietę idea.

  2. 2

    Grill, czyli dopytywanie

    Agent/grill-with-docs

    Agent czyta pomysł i kod, a potem zadaje pytania w komentarzu. Gdy wszystko jest jasne, publikuje komentarz ## Summary: specyfikację tego, co zbudować, i tego, czego nie.

    ↻ Każda Twoja odpowiedź uruchamia kolejną rundę pytań. Na podsumowanie odpisujesz „ok” albo je poprawiasz.

    Start: ideaKoniec: grilled
  3. 3

    Tickety

    Agent/to-tickets

    Agent dzieli podsumowanie na zadania. Zwykle wychodzi jedno, a więcej tylko wtedy, gdy praca wyraźnie się dzieli. Tickety są pod-zgłoszeniami (sub-issues) pomysłu.

    Start: grilledKoniec: backlog na każdym tickecie, który nie czeka na inny
  4. 4

    Implementacja

    Agent/implement + /tdd

    Agent zakłada nową gałąź i pisze najpierw testy, potem kod. Typecheck, testy i build muszą przejść. Otwiera PR z „Closes #N”, czyli powiązany z ticketem, i opisuje w nim decyzje, które podjął sam. Osobny workflow buduje podgląd tej wersji i wkleja link w komentarzu PR-a.

    Start: backlogKoniec: otwarty PR
  5. 5

    Code review

    Agent/code-review

    Drugi agent sprawdza PR: czy robi to, o co prosił ticket, i czy trzyma się standardów repo. Uwagi publikuje w jednym komentarzu.

    Start: PR otwarty przez claude[bot]Koniec: reviewed
  6. 6

    Poprawki po review

    Agent

    Agent wybiera uwagi warte poprawienia i wypycha poprawki. Wypisuje, co poprawił, a co pominął i dlaczego. Na koniec prosi Cię o review.

    Start: reviewedKoniec: done
  7. 7

    Test i decyzja

    Ty

    Otwierasz link do podglądu z komentarza w PR-ze i sprawdzasz zmianę w przeglądarce. Decyzję zapisujesz jako review PR-a.

    ↻ Request changes z uwagami (także przy konkretnych liniach kodu): agent je wprowadza i znów prosi Cię o review. Zwykły komentarz w PR-ze niczego nie uruchamia.

    Start: doneKoniec: Approve
  8. 8

    Merge i wdrożenie

    Automat

    Po Twoim Approve workflow scala PR do master, wdraża aplikację na GitHub Pages, usuwa podgląd i zamyka ticket. Jeśli coś blokuje merge, na przykład konflikt, pisze o tym w komentarzu.

    Start: ApproveKoniec: zmiana na stronie
  • Etap możesz pominąć. Issue, które od razu jest konkretnym zadaniem, oznacz od razu etykietą backlog.
  • Agenci pracują tylko nad PR-ami otwartymi przez claude[bot]. Twoje własne PR-y przechodzą zwykłe review, bez agentów.
  • Właściciel to autor pierwotnego issue z pomysłem. To on dostaje prośby o review i powiadomienia, gdy coś utknie.

Etykiety

Etykiety to stan pracy i zarazem przyciski „dalej”. Ustawia je zwykle agent, na końcu swojego etapu.

EtykietaKto ustawiaCo oznacza
ideaTyNowy pomysł. Uruchamia grill.
grilledagentPomysł jest jasny. Uruchamia podział na tickety.
backlogagent albo TyTicket gotowy do pracy. Uruchamia implementację.
reviewedagentCode review zrobione. Uruchamia poprawki.
doneagentAgenci skończyli. Czeka na Twój test.
needs-humanagent albo automatCoś utknęło. Właściciel dostaje @wzmiankę z opisem.

Repo ma też etykiety do porządkowania zgłoszeń (needs-triage, needs-info, ready-for-human, wontfix). Nie uruchamiają agentów.

Gdy agent utknie

Każdy etap sprawdza na końcu, czy osiągnął swój cel: etykietę, PR albo komentarz. Jeśli nie, albo agent sam uzna, że nie da rady bez człowieka (ticket sam sobie przeczy, testy nie przechodzą), dzieje się to samo:

  • issue albo PR dostaje etykietę needs-human,
  • pojawia się komentarz z @wzmianką właściciela, opisem problemu i linkiem do przebiegu w zakładce Actions.

Jak ponowić: usuń przyczynę i kliknij Re-run jobs przy nieudanym przebiegu w zakładce Actions. W etapie grill wystarczy też nowy komentarz. Każdy przebieg sam zdejmuje needs-human na starcie.

Bezpieczeństwo i koszty

  • Do master nic nie wchodzi bez człowieka

    Reguła na gałęzi master wymaga PR-a, jednej akceptacji i zielonego joba check (typecheck, testy, build). Agenci nie mogą jej obejść. Nowy push po akceptacji ją unieważnia.

  • Agentów uruchamiają tylko współpracownicy

    Repo jest publiczne, więc każdy może czytać i komentować. Etykietę może jednak dodać tylko ktoś z dostępem do repo. Komentarze i review uruchamiają agenta tylko wtedy, gdy ich autor jest właścicielem albo współpracownikiem.

  • Klucz API jest schowany

    Leży w sekretach repo i w logach jest maskowany. Z powłoki, w której agent wykonuje komendy, jest usuwany.

  • Jeden agent na zadanie

    Etapy dla tego samego issue albo PR-a czekają w kolejce, zamiast działać naraz.

  • Koszty

    GitHub Actions jest darmowy dla publicznych repo. Za Claude płacisz za zużyte tokeny, z konta w Claude Console, z miesięcznym limitem ustawionym na workspace. Każdy job ma też limit czasu, od 20 do 45 minut.

Setup krok po kroku

Robisz to raz na repo. Potrzebujesz konta na GitHubie, terminala i dostępu do Claude Console. Są dwie drogi: kreator w terminalu albo te same kroki ręcznie.

Najprościej: kreator w terminalu

Skrypt scripts/setup-wizard.sh prowadzi przez kroki 2–11. Zakłada publiczne repo, otwiera po kolei właściwe strony, mówi, co kliknąć, zapisuje klucz API jako sekret i na końcu sprawdza całość. Komunikaty ma po angielsku. Potrzebuje tylko zainstalowanego gh (krok 1).

git clone https://github.com/shnatyk/snapcap-agentic-poc.git moje-repo
cd moje-repo
git remote remove origin
./scripts/setup-wizard.sh

Możesz go przerwać (Ctrl-C) i uruchomić od nowa. Tam, gdzie się da, sprawdza, co już jest gotowe. Wolisz ręcznie albo chcesz wiedzieć, co kreator robi? Poniżej te same kroki. Kroki 8–10 są opcjonalne.

  1. Zainstaluj i zaloguj GitHub CLI

    Większość kroków korzysta z gh, czyli GitHuba z terminala.

    Gdzie: cli.github.com (na macOS przez Homebrew)

    brew install gh
gh auth login

  2. Załóż publiczne repo z kodem

    Sklonuj projekt, odepnij go od oryginału i wypchnij do własnego publicznego repo.

    git clone https://github.com/shnatyk/snapcap-agentic-poc.git moje-repo
cd moje-repo
git remote remove origin
gh repo create moje-repo --public --source . --push

    Po co publiczne: na darmowym planie GitHub Pages i reguły gałęzi działają tylko w publicznych repo.

  3. Zainstaluj Claude GitHub App

    Kliknij Install, wybierz swoje konto, potem Only select repositories i swoje repo. Zaakceptuj uprawnienia.

    Gdzie: github.com/apps/claude

    Po co: agenci działają jako claude[bot] przez token tej aplikacji. Tylko dzięki temu etykieta ustawiona przez jednego agenta uruchamia kolejnego. Akcje wykonane zwykłym tokenem workflowu nie uruchamiają innych workflowów.

  4. Utwórz workspace w Claude Console i ustaw limit

    Nazwij workspace jak repo. Potem wybierz go na liście, otwórz Spend limits i ustaw miesięczny limit wydatków.

    Gdzie: platform.claude.com → Settings → Workspaces

    Po co osobny: domyślny workspace (Default) nie może mieć limitu wydatków.

    Claude Console to nie to samo co plan Claude

    Plan w aplikacji Claude (np. Team) i Claude Console to osobne produkty, z osobnymi organizacjami i rozliczeniem. Console rozlicza za tokeny. Jeśli zalogujesz się do Console tym samym e-mailem, ale nie masz zaproszenia do firmowej organizacji, Console założy Ci nową, prywatną. Wtedy koszty idą na nią. Żeby płaciła firma, admin firmowej organizacji w Console musi Cię zaprosić.

  5. Utwórz klucz API i zapisz go jako sekret repo

    Kliknij Create key i wybierz workspace z kroku 4. Klucz bez przypisanego workspace'u tu nie zadziała. Skopiuj klucz (zaczyna się od sk-ant-) i wklej go, gdy gh o niego poprosi:

    Gdzie: platform.claude.com → Settings → API keys

    gh secret set ANTHROPIC_API_KEY

    Uwaga: nie wklejaj klucza do czatu, pliku ani komentarza. Jeśli wycieknie, usuń go w Console i utwórz nowy.

  6. Utwórz etykiety i regułę dla master

    ./scripts/setup-repo.sh

    Co robi: tworzy etykiety procesu i regułę: zmiany w master tylko przez PR z jedną akceptacją i zielonym check. Admin repo może ją obejść wewnątrz PR-a, żeby zmergować własny PR (swojego PR-a nie da się zaakceptować). Agenci nie mogą.

  7. Włącz GitHub Pages

    Poczekaj na pierwszy przebieg Deploy w zakładce Actions. Uruchomił go push z kroku 2 i to on tworzy gałąź gh-pages. Potem ustaw Source: Deploy from a branch, gałąź gh-pages, folder / (root).

    Gdzie: Settings → Pages w Twoim repo

  8. Wybierz model

    opcjonalnie

    Domyślnie agenci używają Sonneta. Żeby przełączyć na Opusa:

    gh variable set CLAUDE_MODEL --body opus

    Uwaga: model jest jeden dla wszystkich agentów w repo.

  9. Ogranicz interakcje obcych

    opcjonalnie

    Ustaw Interaction limits na tylko współpracowników (działa do 6 miesięcy). Agenci i tak ignorują komentarze obcych, ale to tylko instrukcja w ich zasadach, a limit blokuje te komentarze całkowicie.

    Gdzie: Settings → Moderation → Interaction limits

    Uwaga: nie testowaliśmy tego z claude[bot]. Jeśli jego komentarze zaczną się sypać, wyłącz limit.

  10. Uruchom aplikację lokalnie

    opcjonalnie

    Tylko jeśli chcesz pracować nad kodem u siebie. Wersja Node jest w pliku .nvmrc.

    npm install
npm run dev

  11. Pierwsza próba

    Załóż issue, na przykład „Let me edit a to-do's title”, z etykietą idea. Odpowiadaj na pytania agenta, a pod podsumowaniem napisz „ok”. Dalej idzie samo, aż dostaniesz prośbę o review.

    Uwaga: każdy przebieg agenta zużywa tokeny z Twojego workspace'u w Console.

Pierwszy przebieg na żywo

Pierwszy pomysł brzmiał „Delete All items” (#1). Po czterech rundach pytań zmienił kierunek: zamiast usuwania wszystkiego powstał przycisk „Clear completed” i sortowanie ukończonych zadań na górę. Od „ok” pod podsumowaniem do merge'a minęło niecałe 7 minut, z czego dwie zajął test i decyzja człowieka.

  1. 0:00Ty„ok” pod podsumowaniem w #1
  2. +0:40Agentetykieta grilled
  3. +1:27Agentticket #4 z etykietą backlog
  4. +2:29AgentPR #5: 5 plików, +40/−3 linii, z testami
  5. +3:22Agentcode review, etykieta reviewed
  6. +4:20Agentpoprawki po review, etykieta done
  7. +4:28Automatprośba o Twoje review
  8. +6:32TyApprove po teście podglądu
  9. +6:41Automatmerge i wdrożenie na stronę

Znane ograniczenia

  • Zwykły komentarz w PR-ze niczego nie uruchamia. Uwagi do PR-a dawaj w review z Request changes.
  • Pomysł (issue z etykietą idea) nie zamyka się sam po merge'u. Zamykasz go ręcznie.
  • Ticket, który czeka na inny, nie dostaje backlog. Dodaj ją ręcznie, gdy blokujący ticket zostanie zmergowany.
  • Tickety robione równolegle mogą się gryźć przy merge'u. Workflow o tym napisze, a rozwiązać musi człowiek.
  • Agenci nie mogą zmieniać plików workflow w .github/workflows/.
  • Agenci nie dodadzą nowej paczki npm: w ich sandboxie package.json i package-lock.json są tylko do odczytu. Ticket, który jej potrzebuje, kończy się etykietą needs-human. Dodaj paczkę na master sam, a potem znów nadaj ticketowi etykietę backlog.
  • Agent ma pełny dostęp do powłoki na serwerze GitHuba i czyta treść issue oraz komentarzy. Trzymaj krótką listę współpracowników.
Pod maską, dla ciekawskich
  • Każdy agent to krok anthropics/claude-code-action w workflowie. Prompt zaczyna się od nazwy skilla, np. /grill-with-docs, a dalej są zasady danego etapu.
  • Wspólne zasady dla wszystkich agentów są w AGENTS.md i docs/agents/. Na przykład: drobne decyzje podejmuj sam i je zapisz, a gdy bez człowieka się nie da, ustaw needs-human.
  • Skille leżą w .claude/skills/ i są w repo, żeby serwer GitHuba je widział.
  • Wszystkie etapy dla jednego issue albo PR-a mają wspólną kolejkę agent-<numer>.
  • Merge robi zwykły token workflowu, który nie uruchamia innych workflowów. Dlatego merge.yml sam woła wdrożenie i usuwa podgląd.
  • GitHub nie umie odfiltrować wyzwalaczy po nazwie etykiety. Każde zdarzenie uruchamia wszystkie workflowy, które go nasłuchują, i większość kończy się jako „skipped”. Po każdym etapie job prune usuwa te puste przebiegi z listy w Actions.
